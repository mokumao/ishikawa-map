# デザイン品質

石川マップの新しいUIや、明示的に対象となった見た目・動きの品質を、既存の精密な調整を壊さず改善する。

このプロジェクトは既存部分が1px単位で調整されている。新規部分には一貫した設計基準を使い、既存部分は対象と根拠を明確にして1箇所ずつ扱う。

## 適用範囲を確認する

- 新しいコンポーネントやページを作る場合は適用する。
- 「見た目を全体的に整えたい」「動きを滑らかにしたい」「デザイン品質を使って」と明示された場合は適用する。
- 「少し右へ」「文字を大きく」など、既存1箇所の単純な微調整には、このSkill全体を持ち込まない。
- 既存部分の広範な改善は、ユーザーがすでに対象範囲を指定している場合を除き、候補を提示して範囲を確認してから進める。
- 既存の調整済みCSS値を、後述の刻み幅へ無断で丸めない。
- 依頼対象外のUIを、気づいたという理由だけでまとめて書き換えない。

## 既存部分を改善するとき

1. コードと実表示を確認し、低リスクで効果の高い候補を洗い出す。
2. ユーザーがまだ対象を決めていない場合は、候補、効果、副作用を提示して優先順位を確認する。
3. 1箇所ずつ修正し、スマートフォン幅375pxを中心に検証する。
4. 問題がなければ次の箇所へ進む。大規模なデザインシステム変更はページや機能単位に分ける。

過去には、設定メニューと写真ライトボックスのフェード化、ミニマップのリサイズ処理のデバウンス化を、この進め方で安全に反映している。

## 原因を特定してから直す

「カクつく」「もっさりする」「貧相に見える」といった感覚だけで全体を書き換えない。

- 利用可能なブラウザ開発者機能、パフォーマンス計測、実表示の観察、コード検索を使う。
- アニメーション不足、レイアウト再計算、過剰なDOM更新、画像サイズ、イベント発火頻度など、実際の原因を絞る。
- 原因と関係する箇所だけを変更する。
- 実機でしか再現しない場合は、確認済みの事実と推定を分け、実機確認が必要な点を明記する。

## 画像を使用するとき

石川マップは素のHTML/CSS/JavaScriptサイトであり、大規模な画像変換パイプラインを前提にしない。画像を追加・表示する機能にだけ次を適用する。

- 表示サイズに対して過大な画像を読み込まない。幅300px表示なら、おおむね300〜600px幅を目安にする。
- 画面外になり得る画像には`loading="lazy"`を付ける。
- 可能ならWebPなど適切な形式を使う。現状規模では手動変換でよく、自動パイプラインを無断で導入しない。
- アイコンやロゴには、適切な場合はSVGを使う。
- `<img>`に`width`と`height`を指定し、読み込み中のレイアウト移動を抑える。

## アニメーションとトランジション

- ホバー、開閉、表示・非表示などの状態変化には、必要な場合だけtransitionを付ける。
- `transition: all`は使わず、対象プロパティを明示する。

```css
transition: transform 0.2s ease-out, opacity 0.2s ease-out;
```

- `transform`と`opacity`を優先し、`width`、`top`、`left`など再レイアウトを起こしやすいプロパティのアニメーションは避ける。
- 急に動く・止まる印象を避け、用途に合う`ease-in-out`や`cubic-bezier`を選ぶ。

### 石川マップのモーション方針

このプロジェクトでは、OSの「視差効果を減らす」設定にかかわらず、アニメーションを維持する方針がユーザー判断で決まっている。

- 新しいアニメーションにも`prefers-reduced-motion`による停止処理を追加しない。
- 一般的なアクセシビリティ推奨と異なる、石川マップ固有の明示的な方針として扱う。
- 方針を見直す場合は、既存挙動を一括変更せず、先にユーザーへ確認する。

### `display`切り替えをフェードさせる

`display: none`と`block`または`flex`を直接切り替えるだけでは、`opacity`の補間に必要な描画状態がなく、開閉の両方を安定してフェードできない。

- 開くとき：先に`display`を設定し、二重`requestAnimationFrame`の中でフェード用クラスを追加する。Safariで1回の`requestAnimationFrame`では遷移が始まらない場合を考慮する。
- 閉じるとき：フェード用クラスを先に外し、transition時間後に`display: none`を設定する。
- 既存実装は`script.js`の`showMain()`／`closeMenu()`、`detail.html`の`openLightbox()`／`closeLightbox()`を参照する。
- タイマーとtransition時間を別々の値にせず、変更時にずれない構造を優先する。

## 新規UIのデザイン基準

新しく作るUIでは、フォントサイズと余白を思いつきの値で増やさず、次の刻み幅を基本にする。

- フォントサイズ：12 / 14 / 16 / 20 / 24 / 32px
- 余白：4 / 8 / 12 / 16 / 24 / 32 / 48px
- 本文の行間：1.5〜1.7を目安にする

必要なら新規CSS変数を定義してよい。ただし、既存CSSへ一括適用するリファクタリングは、対象範囲と影響を説明してユーザーの承認を得てから行う。

新規UIでも、周辺の既存UIと連続して見える箇所では、刻み幅だけでなく実際の位置関係と既存基準を優先する。

## パフォーマンス

- スクロール、リサイズ、連続ズームなど頻繁に発火する処理は、必要に応じて`debounce`、`throttle`、`requestAnimationFrame`による集約を使う。
- イベントの性質に応じて方式を選び、単に遅延させて操作感を悪化させない。
- DOMの読み取りと書き込みを無秩序に交互実行しない。変更は可能な範囲でまとめる。
- ループ内で多数の要素へ個別にインラインスタイルを書き続ける処理を避ける。
- 不要な`console.log`、デバッグ用タイマー、監視処理を本番コードに残さない。
- ページネーションや仮想スクロールは、実測で一覧表示が問題になってから検討する。件数だけを理由に複雑な仕組みを先行導入しない。
- GPU合成のヒントや`will-change`は常用せず、対象と効果を確認して限定的に使う。

## 実装フロー

1. `AGENTS.md`、作業ツリー、対象コード、現在の表示を確認する。
2. 依頼の対象と、変更しない既存部分を明確にする。
3. 見た目やカクつきの原因を調査し、事実と推定を分ける。
4. 最小限の差分で実装する。ユーザーが許可していない周辺改善を混ぜない。
5. 構文、差分、関連する操作を確認する。
6. スマートフォン幅375pxで表示と操作を確認し、影響する場合はデスクトップ幅やiPhone Safari相当の挙動も確認する。
7. CSSやJavaScriptを変更した場合は、`AGENTS.md`のキャッシュバスティング規則に従う。
8. コミット、プッシュ、公開は、ユーザーが明示的に許可した場合だけ行う。

## 完了時の確認

- 今回は新規UIか、意図的な品質改善か。単純な微調整へ過剰適用していないか。
- 原因を確認せず全体を書き換えていないか。
- 既存の調整済み値や対象外UIを変更していないか。
- 画像を使う場合、サイズ、遅延読み込み、寸法指定が適切か。
- transitionの対象プロパティを明示しているか。
- 石川マップ固有のモーション方針を維持しているか。
- 新規UIの余白、文字サイズ、行間に一貫性があるか。
- 頻繁に発火する処理やDOM更新に無駄がないか。
- スマートフォン幅375pxで見た目と操作を確認したか。
- 意図したファイルだけが変更され、既存機能に回帰がないか。
- 外部変更はユーザーから得た権限の範囲内か。
