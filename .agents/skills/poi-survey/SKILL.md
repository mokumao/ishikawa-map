# POI調査

うるま市石川マップへ掲載する店舗・施設を、単一情報源やモデルの記憶に頼らず、複数ルートで発見・検証する。

## 基本原則

1. **単一情報源を信じない。** 発見と検証を複数ルートで行う。
2. **モデルの記憶だけで店舗を列挙・追加しない。** 実在する現在の情報源を開く。
3. **確度で扱いを分ける。** 複数ソース一致は採用候補、1ソースだけなら要検討、不一致なら保留する。
4. **出典と確認日を残す。** 採用する値がどのページのどの記述に基づくか追跡できる状態にする。
5. **調査とデータ変更を分ける。** 調査依頼だけでは`restaurants-data.js`を変更しない。
6. **既存データを勝手に上書きしない。** 修正根拠と差分を示し、依頼・許可の範囲内だけを変更する。
7. **不明を隠さない。** 確認できない値を推測で埋めず、「要確認」または空欄を適切に使う。

## 権限境界

- 「調査」「棚卸し」「確認」の依頼では、候補、根拠、確度、既存データとの差分を報告するところまでとする。
- ユーザーが追加・修正を依頼している場合だけ、データファイルを変更する。
- 既存店舗の店名、住所、営業時間、座標、掲載状態を変更する前に、変更前後と根拠を確認する。
- 既存データの一括是正、削除、`status: hidden`への変更、カテゴリ追加は、対象範囲を明示してユーザーの判断を得る。
- コミット、プッシュ、公開は、ユーザーが明示的に許可した場合だけ行う。
- 調査中に別の誤りを見つけても、依頼対象外なら勝手に混ぜず、別の候補として報告する。

## 禁止する情報源・取得方法

### Googleと電話帳

- **GoogleマップおよびGoogle Places APIを自動取得・スクレイピング・データ転記に使わない。**
- ユーザーがGoogleマップや現地写真で見つけた情報は発見の手がかりとして歓迎するが、掲載値は許可された別情報源で裏取りする。
- `detail.html`の「Googleマップで見る」のような単純な外部リンクは、この自動取得禁止とは別であり維持できる。
- **NTTタウンページ／iタウンページを自動収集しない。** 個別の存在確認に使う場合も、大量取得や内容転記はしない。

### LINE

- LINE公式アカウントを`hours`、`closed`、`note`の転記元にしない。
- 友だち追加が必要で第三者が裏取りしにくく、サービスデータの再利用制限もあるため。
- 単純な案内リンクとして扱う場合も、内容をデータへ転載しない。

### 転記・保管に使わない第三者サイト

次のサイトは、発見や実在確認のヒント、読者向けリンクとして個別に参照できるが、そこに掲載された`hours`、`closed`、`note`などを`restaurants-data.js`へ転記・保管しない。

- 食べログ（tabelog.com）
- エキテン（ekiten.jp）
- Yahoo!地図（map.yahoo.co.jp）
- e-map.ne.jp／いつもNAVI
- NAVITIME（navitime.co.jp）
- ホットペッパー／ホットペッパービューティー（hotpepper.jp）
- ひとさら（hitosara.com）
- Retty（retty.me）
- e燃費（e-nenpi.com）
- マピオン（mapion.co.jp）
- ぐるなび（r.gnavi.co.jp／gnavi.co.jp）
- Yelp（yelp.com）
- じゃらんnet（jalan.net）

これらのサイトでしか情報が見つからない場合は、内容を転記せず「要確認」とする。単純なリンクを`sourceUrl`または`sourceUrls`に掲載する場合も、リンク先の内容を`note`へ書き写さない。

`hours`、`closed`、`note`の転記元として使えるのは、原則として次だけとする。

- 店舗・チェーンの公式サイトまたは公式SNS
- 市区町村・県などの公的機関
- OpenStreetMap
- 店舗主から直接得た情報
- 現地の看板・掲示を人が確認した情報

2026-08-08以前の既存データに禁止サイト由来の内容が含まれる可能性があっても、別途依頼された一括監査なしに今回の調査へ混ぜて書き換えない。

## 未知の情報源サイトを扱う

禁止リストにない新しいドメインを使う前に、利用規約とフッターリンクを確認する。

1. 「サイト名 利用規約」などで規約ページを探す。
2. 複製・転載、第三者提供、自動収集・スクレイピング、保存を禁止する条項を確認する。
3. 明確な禁止条項があればそのサイトを転記元にせず、公式サイトなどへ切り替える。
4. 規約が見つからない、または曖昧なら安全側に倒して保留する。
5. サイト名、URL、該当条文、発見経緯、代替情報源を調査メモへ残す。
6. 調査完了時に禁止候補をまとめて提示し、ユーザーが承認した場合だけCodex版Skillの禁止リストへ追加する。

Skill自体の変更は将来の全調査へ影響するため、調査タスクのついでに無断で書き換えない。

## 調査フロー

### 1. 準備

- `AGENTS.md`、作業ツリー、現在の`restaurants-data.js`と`script.js`のカテゴリを確認する。
- 既存の未コミット変更を保護する。
- 対象カテゴリ、対象地域、求める成果が「調査のみ」か「反映まで」かを確認する。
- 広いカテゴリは適切な単位へ分け、途中結果と未調査範囲を明記する。

### 2. 候補を複数ルートで発見する

#### ルートA：OpenStreetMap／Overpass API

- タグ検索と名前検索を両方行う。タグ不備や表記揺れを拾うため、片方だけにしない。
- 複数のOverpassサーバーを順番に試し、短い回数のリトライ後は時間を置く。無制限に再試行しない。
- `ishikawa-boundary.js`のポリゴンで石川地区内か判定する。
- Codexで利用可能なPythonを使い、リポジトリルートから実行する。結果はシステムの一時ディレクトリへ保存し、リポジトリへ不要な調査ファイルを残さない。

カテゴリに応じて`QUERY`を差し替え、次の形で抽出できる。

```python
# -*- coding: utf-8 -*-
import json, re, tempfile, time, urllib.parse, urllib.request
from pathlib import Path

PROJECT_ROOT = Path.cwd().resolve()
BOUNDARY_JS = PROJECT_ROOT / 'ishikawa-boundary.js'
OUTPUT = Path(tempfile.gettempdir()) / 'ishikawa-map-poi-result.json'
SERVERS = [
    'https://overpass-api.de/api/interpreter',
    'https://overpass.kumi.systems/api/interpreter',
    'https://overpass.private.coffee/api/interpreter',
]
QUERY = '''
[out:json][timeout:60];
(
  node["shop"="convenience"](26.39,127.78,26.47,127.89);
  way["shop"="convenience"](26.39,127.78,26.47,127.89);
  node["name"~"セブン|ローソン|ファミリーマート|ファミマ",i](26.39,127.78,26.47,127.89);
  way["name"~"セブン|ローソン|ファミリーマート|ファミマ",i](26.39,127.78,26.47,127.89);
);
out center;
'''

def load_boundary():
    text = BOUNDARY_JS.read_text(encoding='utf-8')
    return [(float(a), float(b)) for a, b in
            re.findall(r'\[\s*(26\.\d+)\s*,\s*(127\.\d+)\s*\]', text)]

def point_in_polygon(lat, lon, polygon):
    inside = False
    previous = len(polygon) - 1
    for current in range(len(polygon)):
        lat1, lon1 = polygon[current]
        lat2, lon2 = polygon[previous]
        if ((lon1 > lon) != (lon2 > lon)) and \
           (lat < (lat2 - lat1) * (lon - lon1) / (lon2 - lon1 + 1e-12) + lat1):
            inside = not inside
        previous = current
    return inside

def fetch():
    request_data = urllib.parse.urlencode({'data': QUERY}).encode('utf-8')
    last_error = None
    for server in SERVERS:
        for _ in range(2):
            try:
                request = urllib.request.Request(
                    server,
                    data=request_data,
                    headers={'User-Agent': 'ishikawa-map-poi-survey/1.0'},
                )
                with urllib.request.urlopen(request, timeout=90) as response:
                    return json.loads(response.read().decode('utf-8'))
            except Exception as error:
                last_error = f'{server}: {error}'
                time.sleep(5)
    raise RuntimeError(last_error)

boundary = load_boundary()
results = []
for element in fetch().get('elements', []):
    tags = element.get('tags', {})
    lat = element.get('lat') or element.get('center', {}).get('lat')
    lon = element.get('lon') or element.get('center', {}).get('lon')
    if lat is None or lon is None:
        continue
    results.append({
        'name': tags.get('name', ''),
        'brand': tags.get('brand', tags.get('operator', '')),
        'branch': tags.get('branch', ''),
        'shop': tags.get('shop', ''),
        'lat': round(lat, 6),
        'lon': round(lon, 6),
        'osm_id': f"{element.get('type')}/{element.get('id')}",
        'inside': point_in_polygon(lat, lon, boundary),
    })

OUTPUT.write_text(json.dumps(results, ensure_ascii=False, indent=2), encoding='utf-8')
print('output:', OUTPUT)
print('total:', len(results), 'inside:', sum(1 for item in results if item['inside']))
```

ネットワーク利用が制限される環境では、必要な範囲の許可を得て実行する。失敗時に無制限のリトライや別の禁止情報源への切り替えを行わない。

カテゴリ別の基本条件：

| カテゴリ | OSMタグ条件 | 名前検索例 |
|---|---|---|
| コンビニ | `"shop"="convenience"` | セブン\|ローソン\|ファミリーマート\|ファミマ |
| ガソリンスタンド | `"amenity"="fuel"` | ENEOS\|エネオス\|アポロ\|出光\|SS |
| 宿泊 | `"tourism"~"hotel\|guest_house\|hostel\|motel"` | ホテル\|民宿\|リゾート |
| 金融 | `"amenity"~"bank\|post_office"` | 銀行\|郵便局\|JA\|信金 |
| 医療 | `"amenity"~"hospital\|clinic\|dentist\|pharmacy"` | 病院\|医院\|クリニック\|薬局 |
| 教育 | `"amenity"~"school\|kindergarten"` | 小学校\|中学校\|高校\|幼稚園\|こども園 |
| 飲食店 | `"amenity"~"restaurant\|cafe\|fast_food\|bar\|izakaya"` | 食堂\|カフェ\|居酒屋 |
| 美容・理容 | `"shop"~"hairdresser\|beauty"` | 美容室\|理容\|理髪\|床屋\|ヘアー\|HAIR\|サロン\|salon |

新しいカテゴリでは、最初からこの表を変更せず、今回使ったタグ・名前条件と結果を報告する。再利用価値を確認後、ユーザーの許可を得てSkillへ追加する。

#### ルートB：公式一覧とウェブ検索

- チェーン・組織の公式店舗検索で、うるま市または対象地域の一覧を確認する。
- 自治体、業界団体、店舗公式サイトの一覧を探す。
- 禁止第三者サイトは候補発見・件数比較だけに使い、値を転記しない。
- OSMと公式一覧の件数・店名を突合し、片方にしかない候補を個別検証する。

OSMだけでは登録漏れがある。逆に、公式・ポータル一覧にも閉店や重複が混じるため、どちらか一方だけで網羅性を主張しない。

### 3. 既存データと突合する

- `restaurants-data.js`の全データと該当ジャンルを確認し、新規候補と既存店舗を分ける。
- 店名の全角・半角、旧字体、ブランド表記、支店名の揺れを正規化して比較する。
- 電話番号が一致する場合は同一店舗の可能性が高い。
- 住所、電話、公式店舗ID、座標を組み合わせて判断する。
- 座標が近いだけで重複と決めない。同じ施設内や同名チェーンの別店舗があり得る。
- 既存店舗と一致しそうな候補は「新規追加」ではなく「既存データ再確認」として扱う。

### 4. 実在を二段階で検証する

各候補について、次の2つの観点を独立して確認する。サブエージェントや並列検証は、ユーザーが明示的に依頼し、環境上許可される場合だけ使う。それ以外は同じ観点を順番に検証する。

#### 検証員

- 公式店舗検索、公的機関、OSM、店舗公式ページを実際に開く。
- 正式店名、現住所、電話、公式店舗ID、営業継続の痕跡を確認する。
- 住所が石川地区内か、自治体名・大字・境界で確認する。
- 使用したURL、ページ上の根拠、更新日または確認日を記録する。

判定：

- `confirmed`：公式情報、または複数の信頼できる情報源で現在の存在を確認。
- `likely`：信頼できる情報源1件で確認できるが、独立した裏取りが不足。
- `uncertain`：情報が古い、少ない、または矛盾している。
- `not_found`：十分に検索しても現在の存在を確認できない。

#### 懐疑係

掲載すべきでない理由を探す。

1. 閉店・移転・閉店予定の情報がないか。
2. 住所・座標が石川地区外ではないか。
3. 既存掲載との重複ではないか。
4. 公式情報が古い、または現在の店名と一致しない可能性がないか。

反証が見つからなければ`refuted=false`とする。反証がある場合は内容と根拠を残す。

### 5. 確度を決める

確度は調査判断として記録し、スキーマに存在しない`confidence`フィールドを勝手に追加しない。

| 確度 | 目安 | 扱い |
|---|---|---|
| 高／`confirmed` | 公式情報または独立した複数情報源が一致し、反証なし | 掲載候補 |
| 中／`likely` | 信頼できる1情報源で確認、一部項目は未確認 | 内容を限定して候補。未確認値は「要確認」 |
| 低／`uncertain` | 古い情報、矛盾、住所・名称・営業継続に疑義 | 原則保留。存在だけ確認できる場合は`warn: true`候補としてユーザー判断 |
| 不採用／`not_found`または反証あり | 現在の存在を確認できない、地区外、閉店、重複 | 追加しない。既存データ変更は別途確認 |

基本採用条件は`confirmed`かつ`refuted=false`。`likely`を掲載する場合は事実を絞り、確度不足を隠さない。

## 項目別の確認基準

### 店名

- 店舗公式またはチェーン個別店舗ページの現行表記を優先する。
- 看板など新しい現地情報とウェブ上の旧店名が食い違う場合は、現地の実態を優先しつつ、旧店名と未確認点を根拠付きで残す。
- 表記揺れだけで別店舗を作らない。

### 住所

- 都道府県、市町村、大字、丁目、番地を確認する。
- 公式店舗ページ、公的機関、店舗公式情報を優先する。
- 地番と住居表示、全角・半角、ハイフンの違いを区別する。
- 「うるま市」と書かれているだけでは石川地区内と判断しない。大字と境界を確認する。
- 異なる住所が出た場合は、移転、旧住所、施設内住所、表記揺れの可能性を調べ、推測で統合しない。

### 座標

次の順で確認する。

1. 国土地理院住所検索APIで住所から座標を得る。戻り値は`[経度, 緯度]`の順なので入れ替えに注意する。
2. OSM／Overpassの施設座標を確認する。
3. 規約上許される個別スポット情報を補助的に確認する。大量取得はしない。

国土地理院とOSMが30m以内で一致すれば採用可能。原則として施設位置を示すOSM座標を使い、国土地理院が街区代表点の場合はその差を考慮する。片方だけの場合はコメントへ記録し、精度が粗ければ`warn: true`候補とする。

### 営業時間・定休日

実在確認とは別に、次の優先順位で調べる。

1. 店舗公式サイトまたは公式SNS。更新日が新しいものを優先。
2. 市区町村など公的機関。
3. 人が確認した現地看板・掲示。
4. 店舗主から直接得た情報。

- チェーン店では汎用トップページより個別店舗ページを優先する。
- 個別店舗ページの住所と店舗名が対象店舗に一致することを確認する。
- 自動アクセスが拒否される場合は、同チェーンが使う個別店舗ページ基盤を確認する。それでも読めなければ、ユーザー提供の画面や別の公式情報を待ち、推測で埋めない。
- 個別ページに営業時間がなければ、実在確認には使えても`hours`／`closed`の根拠にはしない。
- 確認できない場合は`hours`／`closed`を「要確認」とし、未確認を明示する。
- 季節営業、臨時営業、SNS投稿だけの情報は確認日を重視し、恒常的な営業時間と混同しない。

既知のチェーン店舗検索：

| チェーン | 店舗検索・個別ページ | 注意 |
|---|---|---|
| ファミリーマート | `store.family.co.jp`／`store.family.co.jp/points/XXXXX` | 個別ページに営業時間・設備あり |
| ローソン | `store.lawson.co.jp`／`www.areamarker.com/lawson/info/XXXXX?...` | 自動アクセスが拒否される場合がある |
| セブン‐イレブン | `www.sej.co.jp`／`seven-eleven.areamarker.com/711map/info/XXXXX?...` | 個別ページ基盤を直接確認できる場合がある |
| ENEOS | `eneos-ss.com/search/ss/pc/detail.php?SCODE=XXXXX` | 個別店舗ページを優先 |
| 出光／アポロステーション | `map.idemitsu.com/b/a/info/XXXXX/` | 個別店舗ページを優先 |
| 系列不明のSS | 沖縄県石油商業組合`oki-ss.or.jp/?page_id=167` | 実在・運営会社の参考。営業時間の根拠にはしない |

チェーンが外部の店舗検索基盤を使っている場合でも、その個別ページが対象店舗の公式検索導線であることを確認する。禁止リストにあるe-map.ne.jpなどは、候補発見や店舗検索導線の確認に留め、内容を転記しない。

確認済み値には出典を表示し、「要確認」には出典を付けない。情報源のドメインだけで「公式サイト」と断定せず、確認できない場合はドメイン名を中立的に表示する。地図ポップアップと詳細ページの両方で表示が一致するか確認する。

### `sourceUrl`と`website`

- チェーン店の`sourceUrl`は、可能なら個別店舗ページを使う。
- 個別ページがなければチェーン本部トップを使ってよいが、そのページで確認できない値の根拠にはしない。
- `website`は店舗固有サイトを最優先し、次にチェーン本部。予約導線に実用価値がある場合は予約ページも検討できる。
- `instagram`、`sourceUrl`と同一URLを`website`へ重複入力しない。
- 詳細画面のボタン文言は、運営主体を確認していないURLを「公式サイト」と断定せず、「ウェブサイト」とする。

### `note`

- `note`の各文は、`sourceUrl`または`sourceUrls`のどの記述に基づくか指し示せるものだけにする。
- 複数情報源を使った事実は、そのURLを`sourceUrls`へ残す。
- 「人気」「名物」「愛される」「複雑」「本格」「安全」などの評価語は、出典に同じ評価が明記されていない限り書かない。
- 出典が数字、曜日、名称などの事実断片だけなら、その事実だけを再構成し、評価を加えない。
- 根拠がなければ無理に文章を作らず空欄にする。
- 海、崖、河川など自然環境を「安全」と断定しない。出典にある客観的特徴や注意事項だけを使う。
- 「断定を避ける」ための自作注意文も禁止する。出典に注意事項がなければ創作しない。
- 「○○沿い」「○○の近く」などの立地表現は特に誤生成しやすいため、地図上の印象だけで書かない。
- 読者への行動命令や推奨を書かない。客観的事実を示し、判断は読者に委ねる。
- 電話番号など変更されやすい連絡先を`note`へ転記しない。
- `hours`／`closed`の「要確認」を`note`で重複説明しない。
- 編集経緯は`note`ではなく`revisionHistory`へ書く。

実在確認の二段階検証だけでは`note`の文単位の根拠確認にならない。複数候補を分担する場合も、各文と根拠記述の対応を報告させ、根拠を示せない文を採用しない。

### `warn`

次の場合は`warn: true`候補とする。

1. `hours`または`closed`が「要確認」。
2. 営業継続自体に疑義がある。
3. 店名変更など現行情報として裏取りできない要素がある。
4. 座標や住所の精度が通常より低い。

該当しなければ`warn: false`。警告を乱用しない。`warn: true`でも、追加の注意事実がなければ`note`は空欄でよい。

## データへ反映する前の確認

データ変更が依頼範囲に含まれる場合でも、編集前に次を確認する。

- 新規候補と既存店舗の突合が完了している。
- 店名、住所、座標、営業時間、定休日、情報源、確認日、確度が一覧化されている。
- `confirmed`／`likely`／`uncertain`と反証結果がある。
- 既存値を変更する場合は、変更前、変更後、根拠、影響店舗数を提示できる。
- 閉店や重複を理由に既存データを非表示・削除する場合は、ユーザーの明示的判断がある。
- 調査で判明した内容だけを反映し、未確認項目を推測で埋めていない。
- 禁止サイトの内容を転記していない。

## データ登録ルール

### カテゴリ

追加前に`genre`が`script.js`の`CATEGORIES`配列の大分類・小分類に一致するか確認する。

- 一致する場合は既存ジャンル名を正確に使う。
- 一致しない新業種は、データだけ追加すると`macroOf()`のキャッチオールにより「食事処」扱いになる可能性がある。カテゴリ追加またはsub追加をユーザーに確認し、黙って登録しない。

### `id`、`code`、状態、日付

- `id: 0`は公開テスト店舗専用。実店舗・施設の新規追加は既存データ全体の最大id + 1を使い、地区をまたいだ通し番号とする。
- 掲載終了したidを再利用しない。欠番のまま残す。
- `code`は`都道府県市区町村コード-地区略称-連番`。石川は`IS`。
- codeの連番は`id`と同じ数字をゼロ埋めせずに使い、地区ごとに振り直さない（例：`id: 74`なら`47213-IS-74`）。
- 新地区略称はユーザー確認後に決める。
- `status`は通常`published`。
- `listedDate`は掲載開始日を`YYYY-MM-DD`で設定し、後から変更しない。
- `lastChecked`は確認・修正日であり、再調査のたびに更新できる。
- `tel`は確認できた場合だけ記録する。現状は主に構造化データ用で、画面表示されるとは限らない。
- 表示用店舗番号は`id`をゼロ埋めせずに`detail.html`が生成するため、データフィールドを追加しない。

### 情報源

- 通常は最も信頼できる1件を`sourceUrl`にする。
- 複数リンクを読者へ案内する場合は`sourceUrls`を使う。両方ある場合は`sourceUrls`が優先表示される。
- 第三者サイトをリンクに含めても、その内容を転記してよいことにはならない。
- 情報源ラベルを追加・変更する場合は、ポップアップ側`script.js`と詳細側`detail.html`の両方を確認する。

### `revisionHistory`

既存店舗の読者向け内容を実際に変更した場合に追加する。新規追加や、情報源リンクだけの軽微な追加では不要。

- 古い順を維持し、新しい履歴を配列末尾へ追記する。並べ替えない。
- `lastChecked`と履歴最新日を整合させる。
- `type: "ai"`：具体的な修正内容・文言をCodexが調査・判断した。
- `type: "manager"`：ユーザーが具体的な変更内容・文言を決定した。
- `type: "owner"`：店舗主自身による修正。
- 会話を経たかではなく、具体的な文言を誰が決めたかで分類する。
- 変更前後と根拠を履歴へ書き、編集メモを`note`へ書かない。

### 登録例

```javascript
// ※以下N件は YYYY-MM-DD にOSM抽出＋公式店舗検索等との複数照合で追加
{
  id:          74,                 // 既存データ全体の最大id + 1
  code:        "47213-IS-74",     // 末尾はidと同じ数字（ゼロ埋めなし）
  status:      "published",
  tel:         "",
  lastChecked: "YYYY-MM-DD",
  listedDate:  "YYYY-MM-DD",
  name:        "正式店舗名",
  genre:       "既存ジャンル名",

  hours:       "要確認",
  closed:      "要確認",
```

## 反映と検証

データ変更が許可されている場合だけ行う。

1. `restaurants-data.js`を意図した候補・項目だけ変更する。
2. `index.html`と`detail.html`の`restaurants-data.js?v=`を更新する。
3. `node scripts/generate_sitemap.js`で`sitemap.xml`を再生成する。
4. 構文とデータ件数、id／code重複、最大id、listedDate、カテゴリ一致を確認する。
5. ローカル表示でジャンル別件数、地図ピン、ポップアップ、情報源、警告、`detail.html?id=N`、店舗番号を確認する。
6. 既存店舗を修正した場合は、変更前後と`revisionHistory`を確認する。
7. 差分に対象外ファイルや既存ユーザー変更が混じっていないか確認する。
8. コミット、プッシュ、Pages確認は、ユーザーの明示的許可後に`AGENTS.md`の手順で行う。

## 新しいカテゴリ・禁止サイト・教訓をSkillへ反映する

調査で再利用価値のある新ルールを見つけても、自動的にSkillを書き換えない。

1. カテゴリ名、OSMタグ、名前検索、固有の注意点、規約根拠を候補としてまとめる。
2. ユーザーへ追記案を提示する。
3. 承認された項目だけCodex版Skillへ追加する。

## 過去の調査から得た判断基準

- OSMだけでは店舗を網羅できない。コンビニ調査では14店中4店がOSM未登録だった。
- 地図・ポータルサイト同士でも電話や店舗名の取り違えがあるため、複数照合が必要。
- 同名チェーンの座標違いを即重複と判断しない。公式一覧で別店舗と確認できる場合がある。
- 国土地理院住所検索APIは座標の裏取りに有効だが街区代表点の場合がある。OSM施設座標と比較する。
- 全角・半角、地番・住居表示、旧店名・新店名の表記揺れを確認する。
- Overpassは混雑する。ミラー、限定回数のリトライ、時間を置く方法を使う。
- OSMにもウェブポータルにも載らない小規模店は自動調査では発見できない。ユーザーの現地情報を候補として受け取り、別情報源で裏取りする。
- 看板とウェブの店名が違う場合は移転・改称を疑い、現地の新しい実態を重視しつつ旧店名と確度を記録する。
- `note`の「名物」「人気」「安全」「複雑」などは、事実が正しくても出典にない評価なら書かない。
- 自作の注意喚起も根拠のない創作になり得る。出典にない場合は空欄にする。
- `hours`／`closed`が要確認であることを`note`へ重複記載しない。
- 電話確認の推奨など、読者への行動要求を`note`へ書かない。
- 公共施設は地区紹介調査から見つかることがある。掲載候補として記録し、このSkillの手順で別途検証する。
- 1店舗追加でも公開ページが増えるため、サイトマップ再生成を忘れない。

## 完了条件

- 候補を複数ルートで発見し、既存データと突合した。
- 各候補に実在判定、反証確認、確度、根拠URL、確認日がある。
- 住所、座標、営業時間、定休日を項目別基準で確認した。
- 禁止情報源から`hours`、`closed`、`note`を転記していない。
- `note`の各文を出典へ結び付けられる。
- 調査のみの場合、データファイルを変更していない。
- 反映した場合、既存値を無断で上書きしていない。
- id、code、genre、listedDate、lastChecked、warn、revisionHistoryがルールに沿う。
- キャッシュ番号、サイトマップ、地図・詳細表示を確認した。
- コミット、プッシュ、公開はユーザーの許可範囲内である。
