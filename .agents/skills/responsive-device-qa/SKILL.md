# 端末別レスポンシブ品質確認

石川マップの画面変更を、特定機種だけに合う調整にせず、小型iPhoneから大型Androidまで操作可能な状態にする。`$design-quality`が見た目や動きの設計を扱うのに対し、このSkillは端末差と表示状態の検証を担当する。

## 変更前に確認する

- 対象UIと、変更しない端末・状態を明示する。
- 画面幅だけで機種を推定しない。必要に応じて`innerWidth`、`innerHeight`、`screen.width`、`screen.height`、`visualViewport`、`devicePixelRatio`を実測する。
- ブラウザのアドレスバー、表示倍率、ホーム画面追加、埋め込み表示により、同じ端末でも表示領域が変わる前提で考える。
- 機種名やUser-Agentによる分岐は避け、利用可能な領域、UIの重なり、入力方式など実際に必要な条件で分岐する。

## 実装方針

- 固定UIは、ヘッダー、下部タブ、カテゴリーボタン、セーフエリアとの間に余白を確保する。
- `100vh`だけに依存せず、対応環境では`dvh`や`visualViewport`も検討する。
- `env(safe-area-inset-*)`が関係する端末では、ノッチやホームインジケーターを考慮する。
- 可能なら固定した機種別px値より、コンテナ、`clamp()`、CSS Grid/Flexbox、利用可能領域から計算する方式を優先する。
- 実測による端末クラスが必要な場合は、境界値の根拠を記録し、対象外端末へのフォールバックを残す。
- 既存の調整済みブレークポイントをまとめて書き換えず、原因に関係する条件だけを変更する。

## 確認する画面寸法

影響範囲に応じ、少なくとも小型・標準・大型のスマートフォンを確認する。石川マップでは次を基準値として使う。

| 区分 | CSS表示寸法の目安 | 主な目的 |
|---|---:|---|
| 小型iPhone | 320×568 | 縦方向の見切れ確認 |
| 実測iPhone SE | screen 320×568 | 小型端末の実機基準 |
| 実測iPhone 16e | screen 320×693 | 表示倍率を含む大型iPhone基準 |
| 小型Android | 360×640 | 狭く短いAndroidの確認 |
| 標準Android | 360×800 | 一般的な縦長画面の確認 |
| 大型スマートフォン | 393×852 / 412×915 | 縦長・横幅広めの確認 |

特定の数値を通すこと自体を目的にしない。新しい実機値が得られた場合は、既存の分類と矛盾しないか確認してから基準を更新する。

## 状態別の確認

静止した初期画面だけで完了としない。変更対象に関係する状態を切り替えて確認する。

- ヘッダーの表示中／折りたたみ後
- カテゴリーボタンの表示中／非表示
- 地図／店名／一覧の各タブ
- ポップアップ、案内、設定メニューの開閉前後
- 地図のパン・ズーム後
- 端末の縦向き。横向き対応へ影響する変更では横向きも確認
- 固定UI同士の重なり、画面外への見切れ、タップ領域、スクロール阻害

## 検証と報告

1. ローカルプレビューで対象寸法を再現し、画面またはスクリーンショットを目視する。
2. 変更対象の前後状態を操作し、位置と重なりを確認する。
3. CSSやJavaScriptを変更したら`AGENTS.md`のキャッシュバスティング規則に従う。
4. 公開後はGitHub Pagesの成功と新しい`?v=`の配信を確認する。
5. 実機依存の問題は、必要に応じて診断表示で数値を取得し、対象端末の写真で最終確認する。

シミュレーション確認と実機確認を明確に区別する。実機写真をまだ確認していない段階で「実機で修正済み」「確実に直った」と報告しない。確認できた事実、推定、残っている実機確認を分けて伝える。

## 完了条件

- 対象端末でUIが画面外に切れていない。
- 固定UI、カテゴリーボタン、下部タブ、ポップアップが重なっていない。
- 対象外として維持すると決めた端末の配置が変わっていない。
- 操作後の状態でも表示が崩れず、必要なボタンへ指が届く。
- ローカル確認、公開反映確認、実機確認のどこまで完了したかが報告に明記されている。
