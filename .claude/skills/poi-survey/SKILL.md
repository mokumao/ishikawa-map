# POI調査スキル（店舗・施設データの収集・検証・追加）

うるま市石川マップに掲載する店舗・施設情報を、**人の目に頼らず・複数情報源のクロス照合**で
できるだけ正確に収集するための標準手順。2026-07-21のコンビニ調査（3店→14店）で確立した。

## 設計思想

1. **単一の情報源を信じない** — 発見も検証も必ず複数ルートで行う
2. **AIの記憶から店舗を列挙しない** — 網羅性がなく、実在しない店舗を生成する危険もある
3. **確信度で扱いを分ける** — 複数ソース一致=掲載 / 1ソースのみ=要検討 / 不一致=保留
4. **出典と確認日を必ず記録** — restaurants-data.js のコメントと sourceUrl に残す
5. **人の目は事後訂正に回す** — 読者・管理人からの間違い報告が最後の安全網

## 禁止事項（重要・2026-08-08大幅改定）

- **Googleマップ／Google Places APIの自動利用は禁止**（規約上、スクレイピング禁止・
  Google以外の地図への表示禁止）。人間が見て気づいたことのヒントとしてのみ扱い、
  必ず他ソースで裏取りする
  - ※これは「データの自動取得・転記」の禁止であり、`detail.html`等にある
    「Googleマップで見る」ボタン（`https://www.google.com/maps/search/?api=1&query=...`
    でGoogleマップのサイトへ単純にリンクするだけの仕組み）とは別の話。単純な外部
    リンクはGoogle公式のブランドガイドラインで明示的に歓迎されており問題ない
    （2026-08-09確認）
- **LINE公式アカウントは、`hours`/`closed`/`note`の情報源（転記元）にはしない**
  （2026-08-09判断）。LINEヤフー共通利用規約第14条に「当社サービスやそれらを
  構成するデータを、その提供目的を超えて利用することはできない」という再利用
  制限があり、食べログ等と同種のリスクがあると判断したため。加えて実務上も、
  友だち追加しないと営業時間等の詳細が見えないページが多く、第三者が裏取り
  しにくい。店への案内リンク（Instagram等と同格のリンク欄）として貼ること
  自体は妨げないが、今のところ実際に使う場面は想定していない
- **NTTタウンページ（iタウンページ）の自動収集は禁止**（規約）。個別確認のみ可
- **以下の第三者サイトも、自動取得したデータを`restaurants-data.js`に転記・保管
  することは禁止**（2026-08-08、各サイトの利用規約を実際に確認したところ、
  食べログ以下すべてに「複製・転載・保管の禁止」条項があることが判明した。
  2026-08-09にぐるなび・Yelpの2件、2026-08-11にじゃらんnetを追加確認）：
  食べログ（tabelog.com）、エキテン（ekiten.jp）、Yahoo!地図（map.yahoo.co.jp）、
  e-map.ne.jp（いつもNAVI）、NAVITIME（navitime.co.jp）、
  ホットペッパー／ホットペッパービューティー（hotpepper.jp）、
  ひとさら（hitosara.com）、Retty（retty.me）、e燃費（e-nenpi.com）、
  マピオン（mapion.co.jp）、ぐるなび（r.gnavi.co.jp／gnavi.co.jp、第7条13号で
  無断転載・蓄積・複製を禁止）、Yelp（yelp.com、Business Terms等でスクレイピング・
  自動収集を禁止）、じゃらんnet（jalan.net、宿泊施設等予約サービスご利用規約
  第5条1項で「私的利用以外の目的での複製・送信」「第三者による利用」を禁止）
  - これらのサイトは、GoogleマップやNTTタウンページと**同じ扱い**にする：
    実在確認・発見の手がかり（「このサイトにこの名前・住所で載っている」）
    としてのみ使い、`hours`/`closed`/`note`等に転記する出典にはしない
  - 単純にリンクを貼ること自体（読者を当該ページへ案内するだけで、内容を
    複製・保存しない）は、規約上の「複製・保管」には当たらないと考えられる
    ため、`sourceUrl`/`sourceUrls`にリンクとして載せること自体は妨げない。
    ただし新規にそのサイトの内容を読み取ってnote等の文章として転記するのは禁止
  - `hours`/`closed`/`note`の実際の出典（転記元）は、**公式サイト（チェーン・
    店舗自身）／公的機関（市区町村・県等）／OSM／店舗主から直接得た情報**に限る
  - 2026-08-08以前に追加した既存データは、上記サイトから転記した内容を含んでいる
    可能性が高いが、この時点では現状維持とし、別途まとまった調査・是正作業を行う
    （このSKILL.md改定は「今後の新規追加・更新」への適用が目的）

## 新規情報源サイトの規約自動チェック（2026-08-11新設）

これまでは第三者サイトの規約違反が発覚するたびに都度ユーザーと相談しながら
禁止リストに追加してきたが、非効率なため以下のフローに変更する。

**調査中（Step1の発見時・Step3.5の営業時間調査時、都度・自動で実行する）**

1. 新しい情報源のURL・ドメインが出てきたら、まず上の「禁止事項」の
   禁止サイト一覧と照合する。一致すれば当然使わない（従来通り）
2. リストに無い未知のドメインの場合のみ、その場で利用規約ページを
   検索・取得し（「サイト名 利用規約」等で検索、サイトのフッターリンクも
   確認する）、「複製・転載」「第三者への提供」「自動収集・スクレイピング」
   を禁止する条項が無いか確認する
3. 判定結果で対応を分ける：
   - **明確な禁止条項あり** → そのデータ収集ではこのサイトを使わず、
     他の情報源（公式サイト等）で代替する。同時に、サイト名・URL・
     該当条文・発見の経緯を会話内の一時メモとして記録する
     （＝下記「調査完了時」でまとめて報告する候補になる）
   - **規約に問題なし** → 通常通り情報源として使用してよい
   - **規約ページが見つからない・文言が曖昧** → 安全側に倒して保留とし、
     他の情報源で代替する（頻度が低ければその場でユーザーに個別確認してもよい）

**調査完了時（その回の調査が終わったタイミングで1回だけ）**

4. 上記3で「禁止候補」としてメモしたサイトが1件以上あれば、チャットで
   まとめて提示する。候補が0件だった回はこの報告自体を省略する。
   提示フォーマット：
   ```
   今回の調査で、禁止リスト未登録の新しい情報源サイトがN件見つかりました。

   - サイト名：〇〇〇〇
   - URL：https://〇〇〇〇.com/
   - 該当条文：利用規約 第△条△項「〜」
   - 経緯：（店舗名）の営業時間調査でこのサイトを参照しようとして発見
   - 対応：このデータでは使用せず、公式サイト等の別情報源に切り替え済み

   禁止リストに追加してよろしいですか？
   ```
5. ユーザーが承認したものだけ、その場で上の「禁止事項」の禁止サイト一覧に
   1回のEdit操作でまとめて追記する（Step 5の反映・pushより前に済ませる）
6. 否認されたものは追加しない（次回また同じサイトが出てきたら再度チェックする）

将来的に（未実装）定期的な自動再調査を行う場合も、この手順で見つかった
禁止候補は`PushNotification`ツールでユーザーに通知する方針（2026-08-11合意）。

### Step 1: 発見（必ず複線で）

**ルートA: OpenStreetMap（Overpass API）**

下記スクリプトを実行（scratchpadに保存して `python` で実行）。ポイント：
- サーバーは混雑しやすい（特に夜）。複数サーバー×リトライで叩く
- **タグ検索と名前検索の両方**を行う（タグ不備の登録を拾うため）
- `ishikawa-boundary.js` の境界ポリゴンで点内判定し石川地区内に限定

```python
# -*- coding: utf-8 -*-
import json, re, time, urllib.request, urllib.parse

BOUNDARY_JS = r'C:\Users\user\OneDrive\デスクトップ\Claude code関連\ishikawa-boundary.js'
SERVERS = [
    'https://overpass-api.de/api/interpreter',
    'https://overpass.kumi.systems/api/interpreter',
    'https://overpass.private.coffee/api/interpreter',
]
# ↓カテゴリに応じて書き換える（下の「カテゴリ別クエリ」参照）
QUERY = '''
[out:json][timeout:60];
(
  node["shop"="convenience"](26.39,127.78,26.47,127.89);
  way["shop"="convenience"](26.39,127.78,26.47,127.89);
  node["name"~"セブン|ローソン|ファミリーマート|ファミマ",i](26.39,127.78,26.47,127.89);
  way["name"~"セブン|ローソン|ファミリーマート|ファミマ",i](26.39,127.78,26.47,127.89);
);
out center;
'''

def load_boundary():
    text = open(BOUNDARY_JS, encoding='utf-8').read()
    return [(float(a), float(b)) for a, b in
            re.findall(r'\[\s*(26\.\d+)\s*,\s*(127\.\d+)\s*\]', text)]

def point_in_polygon(lat, lon, poly):
    n, inside, j = len(poly), False, len(poly) - 1
    for i in range(n):
        yi, xi = poly[i]; yj, xj = poly[j]
        if ((xi > lon) != (xj > lon)) and \
           (lat < (yj - yi) * (lon - xi) / (xj - xi + 1e-12) + yi):
            inside = not inside
        j = i
    return inside

def fetch():
    data = urllib.parse.urlencode({'data': QUERY}).encode('utf-8')
    last = None
    for url in SERVERS:
        for _ in range(2):
            try:
                req = urllib.request.Request(url, data=data,
                    headers={'User-Agent': 'ishikawa-map-poi-survey/1.0'})
                with urllib.request.urlopen(req, timeout=90) as r:
                    return json.loads(r.read().decode('utf-8'))
            except Exception as e:
                last = f'{url}: {e}'; print('retry...', last); time.sleep(5)
    raise RuntimeError(last)

poly = load_boundary()
out = []
for e in fetch().get('elements', []):
    t = e.get('tags', {})
    lat = e.get('lat') or e.get('center', {}).get('lat')
    lon = e.get('lon') or e.get('center', {}).get('lon')
    if lat is None: continue
    out.append({'name': t.get('name',''), 'brand': t.get('brand', t.get('operator','')),
                'branch': t.get('branch',''), 'shop': t.get('shop',''),
                'lat': round(lat,6), 'lon': round(lon,6),
                'osm_id': f"{e.get('type')}/{e.get('id')}",
                'inside': point_in_polygon(lat, lon, poly)})
json.dump(out, open(r'C:\Users\user\AppData\Local\Temp\claude\poi_result.json','w',
          encoding='utf-8'), ensure_ascii=False, indent=2)
print('total:', len(out), 'inside:', sum(1 for p in out if p['inside']))
```

| 金融 | `"amenity"~"bank\|post_office"` | 銀行\|郵便局\|JA\|信金 |
| 医療 | `"amenity"~"hospital\|clinic\|dentist\|pharmacy"` | 病院\|医院\|クリニック\|薬局 |
| 教育 | `"amenity"~"school\|kindergarten"` | 小学校\|中学校\|高校\|幼稚園\|こども園 |

### Step 2: 既存データとの突合

`restaurants-data.js` の該当ジャンルの既存掲載と照合し、新規候補だけを抽出する。

### Step 3: 検証（Workflowで並列実行）

各候補に対し「検証員」と「懐疑係」の2段構えで照合する。使用したプロンプト原文：

**検証員プロンプト**
```
あなたは沖縄県うるま市石川地区の地図サイトのデータ検証員です。
次の（カテゴリ）候補が実在するかをウェブ検索で検証してください。

候補: （店舗名）／ブランド／座標／OSM登録ID／住所・電話の手がかり

調査方法:
- WebSearch/WebFetchツールを使う
- 公式の店舗検索や「(名称) うるま市石川」の検索で正式名・住所を特定
- 緯度経度は下の「座標の取得方法」に従う（Googleマップのデータは使わない）
- 住所が石川地区（うるま市石川○○・伊波・嘉手苅・山城・東恩納・
  赤崎・白浜・曙・東山）であることを確認する

判定基準:
- confirmed: 公式または複数の信頼できる情報源で現在の存在を確認
- likely: 1つの信頼できる情報源で確認
- uncertain: 情報が少なく確信が持てない
- not_found: 検索しても存在の痕跡がない
```

**懐疑係プロンプト**
```
あなたは懐疑的な検証員です。次の店舗情報に「掲載すべきでない理由」が
ないか、ウェブ検索で反証を探してください。

確認する反証:
1. 閉店・閉店予定の情報はないか（「(店名) 閉店」等で検索）
2. 住所・座標が石川地区外（恩納村・金武町・具志川など）ではないか
3. 既存掲載店との重複ではないか（住所・電話番号の違いで判断）

反証が見つからなければ refuted=false。
```

**採用基準**: confirmed かつ refuted=false → 掲載。
likely → 内容次第で掲載（noteは控えめに）。uncertain/not_found → 保留。
座標は複数ソースが30m以内で一致することを確認する。

**座標の取得方法（この順で試す）**

1. **国土地理院の住所検索API（第一候補）** — 国の公的機関のサービスで、
   規約上の懸念がなく、curlで即座に使える。住所さえ分かれば座標が得られる

   ```bash
   curl -s "https://msearch.gsi.go.jp/address-search/AddressSearch?q=$(python3 -c "import urllib.parse;print(urllib.parse.quote('沖縄県うるま市石川曙2-1-55'))")"
   ```

   返り値の `coordinates` は **[経度, 緯度] の順**（lng, lat）なので入れ替えに注意。
   レスポンスの `title` は文字化けして見えることがあるが、座標は正しいので気にしない。

2. **OpenStreetMap（Step 1のOverpass抽出結果）** — 施設そのものの位置に
   置かれていることが多く、ピンの見た目としては最も正確

3. マピオン・ポストマップ・ホームメイト等のスポットページ
   （NAVITIMEは403で拒否されることがある。大量取得はしない）

**1と2が30m以内で一致すれば採用してよい。** 採用するのは原則OSM側の座標
（国土地理院は街区の代表点を返すため、建物から数十m離れることがある）。
どちらか一方しか得られない場合は、その旨をデータのコメントに残す。

### Step 3.5: 営業時間・定休日の調査

実在確認（Step3）とは別に、営業時間・定休日は次の優先順位で調べる。

**優先順位（2026-08-08改定）**
1. 店舗公式サイト・公式SNS（最新の投稿を優先。更新日を確認する）
2. うるま市公式サイト等、公的機関のページ（該当する場合）
3. 現地の看板・掲示（自分の目で確認した場合）
4. 店舗主から直接得た情報

**チェーン店のsourceUrlは「個別店舗ページ」を優先する（2026-08-11新設・改訂）**
コンビニ・ガソリンスタンド等のチェーン店で、sourceUrlがチェーン本部の
汎用トップページ（例：`https://www.family.co.jp/`）になっていると、
情報源ボタンを押しても該当店舗の情報にたどり着けない（ユーザー指摘、
ファミリーマート石川白浜店で発覚。同様の問題がローソン・セブンイレブン・
ガソリンスタンド計12件で見つかり、2026-08-11に一括是正済み）。
チェーンの公式サイトに店舗検索機能がある場合は、**必ずその店舗固有の
ページを探してsourceUrlに使う**。

- **手順**：チェーン公式サイトのトップページ（`website`フィールドの値）を開き、
  ナビゲーション内の「店舗検索」を探す→店舗名で検索→該当店舗の詳細ページに
  遷移し、住所・営業時間の記載が現行データと一致するか確認する
- **判明している大手チェーンの店舗検索URL（2026-08-11時点で確認済み）**：

  | チェーン | 店舗検索の入口 | 個別ページのURL形式 | 備考 |
  |---|---|---|---|
  | ファミリーマート | `store.family.co.jp` | `store.family.co.jp/points/XXXXX` | 自社ドメイン。営業時間・設備の記載あり |
  | ローソン | `store.lawson.co.jp`（自動アクセスは拒否されやすい） | `www.areamarker.com/lawson/info/XXXXX?addresscode=47213&shopid=XXXXX` | 実体は`areamarker.com`という外部プラットフォーム上で運用されている。営業時間の記載あり |
  | セブン‐イレブン | `www.sej.co.jp`→フッターの「店舗検索」 | `seven-eleven.areamarker.com/711map/info/XXXXX?addresscode=47213&shopid=XXXXX` | ローソンと同じ`areamarker.com`基盤（別サブドメイン）。営業時間の記載あり |
  | ENEOS | `eneos-ss.com` | `eneos-ss.com/search/ss/pc/detail.php?SCODE=XXXXX` | 自社ドメイン |

- **自動アクセスがブロックされる場合の対処**：`store.lawson.co.jp`や
  `www.sej.co.jp`のトップページ自体はbot対策で`WebFetch`/自動ブラウザ操作が
  拒否されることがある（`ECONNRESET`等）。この場合、上記表の実際のURL形式
  （`areamarker.com`等）を直接開けば取得できることが多い。それでも失敗する
  場合は、ユーザーに実際のブラウザでスクリーンショットを撮ってもらう、
  という方法も有効（今回、ユーザー提供のスクリーンショットで営業時間表示を
  確認できたことがきっかけで正しいURL形式が判明した）
- 個別店舗ページが見つからない場合のみ、汎用トップページのままでよい
  （`website`フィールドの基準と同じ考え方）
- 新規追加時だけでなく、**既存データを見直す際にも同じ基準を適用する**
  （汎用トップページのまま放置しない）
- 個別店舗ページはあっても営業時間の記載が無い場合（業界団体サイト等）は、
  実在確認・運営会社名の裏付けとしては使えるが、hours/closedの出典には
  ならない。その場合hours/closedは「要確認」のまま（無理に転記しない）

**食べログ・エキテン・Yahoo!地図・NAVITIME・ホットペッパー・ひとさら・Retty・
e燃費・マピオン・e-map.ne.jp・ぐるなび・Yelp等の第三者サイトは、この優先順位から
除外する（2026-08-08・2026-08-09・上記「禁止事項」参照）。** 実在確認や店名・住所のヒントを
得るために閲覧するのはよいが、そこに書かれているhours/closed/noteの内容を
転記してはいけない。これらのサイトでしか情報が見つからない場合は、
無理に転記せず「要確認」のまま掲載する。

**記録のルール**
- どの情報源で調べたかをsourceUrlに記録する
  （現地確認の場合は、noteまたは専用フィールドに「現地確認」と記す）
- 調べた日付をlastCheckedに記録する
- どこにも情報が見つからない場合、hours / closedは空文字にせず
  「要確認」と入れる（未調査であることを示すため）

**表示上の扱い（2026-08-03改定・重要）**
- **営業時間・定休日・備考のすべてに、確認済みの値には必ず出典を表示する。**
  「要確認」のときだけは出典を付けず、そのまま「要確認」と正直に表示する
  （未調査であることを隠さない）
- 出典の見せ方は3パターン：
  1. 食べログ・エキテン等、既知の第三者サイト → その固有名
     （例：「情報源：食べログ」）
  2. うるま市公式サイト（`city.uruma.lg.jp`） → 「情報源：うるま市公式サイト」
  3. 上記以外（店舗独自サイト等） → **「公式サイト」と決めつけず、
     ドメイン名をそのまま表示する**（例：「情報源：cave.okinawa」）。
     機械的にsourceUrlのドメインを見ているだけで、実際に公式か確認した
     わけではないため、誤って「公式」と断定表示しないための方針
- **地図の小さいポップアップ（画面①）と、店舗詳細ページ（画面②）の
  両方に出典を表示する。** 以前はポップアップ側に出典表示が無く、
  詳細ページにしか無かったが、2026-08-03に両方へ統一した
- 実装は `script.js`（ポップアップ用）と `detail.html`（詳細ページ用）に
  それぞれ`sourceSiteLabel()`相当の関数がある（コードが別ファイルなので
  二重管理。新しい第三者サイト・公式ドメインを追加するときは**両方**直す）
- **`website`フィールド（詳細ページのリンクボタン）も同じ方針（2026-08-07追記）**。
  ボタンの文言は「公式サイト」ではなく**「ウェブサイト」**と中立的に表示する
  （`detail.html`の該当箇所）。運営者名の記載確認等、実際にその事業者本人が
  運営していると裏取りできたわけではない（ドメイン名や内容から推測している
  だけの）URLがほとんどのため。ユーザー指摘を受けて2026-08-07に、
  sourceUrl側の方針と揃える形で修正した

**`website`フィールドに何を入れるかの基準（2026-08-10新設）**
1. **最優先：店舗・施設固有のサイト**（その店自身の住所・営業時間・メニュー等が
   書かれているページ）。チェーン店でも支店ごとの個別ページがあればそちらを優先する
2. **次点：チェーン本部の公式サイト**（支店固有ページが存在しない場合）。
   ローソン・ファミマ等、支店ごとのページが無いチェーンでは本部の公式サイトを
   入れてよい。「ウェブサイト」という表示自体が元々「公式サイトと断定しない
   中立的な表現」として設計されているため、支店固有でなくても問題ないと判断
3. **例外：予約導線として価値がある場合**（ホテルの予約サイト等）は、
   支店固有でなくても実用的な価値があるため採用してよい
4. **重複入力の禁止：** `instagram`・`sourceUrl`と同じURLを`website`にも
   重ねて入れない。唯一の情報がInstagramだけの場合は`instagram`フィールドのみに
   入れ、`website`は空欄のままにする（`detail.html`側で同一URLの重複ボタン表示は
   自動的に除去される仕組みも別途あるが、データ入力の時点で重複させないのが望ましい）

**採用基準（2026-08-08改定）**
- 公式サイト・公的機関・OSM・現地確認・店舗主からの情報 → そのまま掲載してよい
- 上記が無く、食べログ等の第三者サイトでしか確認できない → 転記せず
  「要確認」のまま掲載する（第三者サイトへのリンクを`sourceUrls`に
  参考として添えるのは構わないが、そこから内容を書き写さない）
- 情報源なし → 「要確認」のまま掲載し、隠さない

**`warn`（⚠️要確認マーク）を付けるかどうかの基準（2026-08-08新設）**
`warn: true`にすると、ジャンル横に「⚠️ 要確認」バッジが付き、備考が
目立つオレンジ色の枠で表示される。乱用すると本当に重要な警告が埋もれる
ため、以下の基準で判断する。

`warn: true`にすべきケース：
1. `hours`または`closed`のいずれかが「要確認」（出典で確認できなかった）
2. 営業時間・定休日は分かっていても、出典側に**営業を継続しているか自体**
   への疑義がある（例：食べログの「営業状況未確認」表示）
3. 店名変更など、現在の情報として裏取りしきれない要素が残っている
4. 座標・住所の精度が、通常より粗い精度でしか確認できていない

上記のいずれにも当てはまらなければ`warn: false`（通常表示）にする。

**warn:trueのときのnoteの書き方**
- **`hours`/`closed`が「要確認」であることを伝えるためだけに、noteにも
  「営業時間・定休日は要確認」等と重複して書かない。** `hours`/`closed`
  フィールド自体が自動的に⚠️付きオレンジ文字で表示されるため、noteで
  同じことを繰り返すのは冗長（2026-08-08、13件でこの重複が見つかり是正した）
- noteには、hours/closedの表示だけでは伝わらない**追加の注意事項**
  （営業継続への疑義、名称変更の経緯、座標精度の注意点等）がある場合のみ書く
- 追加で書くべき内容が無ければnoteは空欄でよい（空欄時は「Googleマップや
  公式サイト、情報源をご確認ください」と自動表示される）

**情報提供の2本柱（2026-08-08・重要）**
このサイトの情報提供は、次の2本柱を基本とする。
1. **他サイトに導く／他サイトの情報を転記する**：`sourceUrl`・`sourceUrls`の
   リンクで出典に読者を案内することを基本とし、出典で確認できる事実のみを
   `note`等に転記する
2. **店舗主から得た情報は、店舗主からの情報として記載する**：`detailText`等、
   店舗主自身が提供した内容は、その旨が分かる形で扱う

この方針から、以下を徹底する。
- **`note`に読者への行動の呼びかけ（「〜を推奨」「〜してください」等）を
  書かない**。備考は場所そのものの客観的な事実の記述に徹する
  （例：「訪問前に電話確認を推奨」ではなく、単に「食べログに営業状況
  「未確認」の記載あり」という事実だけを書き、判断は読者に委ねる）
- **電話番号など、店舗側の都合で変更されうる個別の連絡先情報を`note`に
  転記しない**。出典側の情報が更新されれば`sourceUrl`のリンク経由で
  自動的に最新情報を読者に届けられるが、`note`に転記した時点の値は
  更新されないまま古くなるリスクがあるため
  （2026-08-08、GENCO・照らす家石川店・ガソリンスタンド3件のnoteに
  あった「〜を推奨」「電話番号」の記載をユーザー指摘で削除した際に
  この方針を明文化した。なお`tel`フィールドは現状、画面表示には
  一切使われておらず、JSON-LD構造化データ用の裏方フィールドである点に
  注意。「telに入れれば読者に伝わる」わけではない）

**noteの内容は必ず出典で裏取りする（2026-08-05・重要）**
2026-05-30に追加された石川ビーチのnoteに「リーフ内は砂地で安全」という、
登録されているsourceUrlには存在しない文言が含まれていることが判明した
（別サイトの類似文言との混同が疑われる。「海が安全」という断定自体も
不適切だった）。この教訓から、以下を徹底する。

- `note`に書く内容は、**`sourceUrl`または`sourceUrls`のいずれかで実際に
  確認できる文言のみとする**（複数の情報源を照合した結果をnoteに書く場合、
  事実を拾った情報源は必ず`sourceUrls`に含める。「検証時に確認したが
  出典には残していない」という状態を作らない）
- 海・崖・河川など自然環境については、たとえ出典に「安全」といった
  趣旨の記載があっても、断定的な安全表現をそのまま転記しない。
  「〜な特徴がある」等の客観的な記述に留めるか、注意喚起の文言にする
- **「断定を避ける」は「自分で言い換えてよい」という意味ではない（2026-08-06追記）**。
  不適切な文言（安全断定・創作内容など）を削除・修正するときも、書き換え後の
  文言は必ず出典に実際にある表現に基づくこと。出典に注意喚起の記載がある場合は
  その内容を使う。出典に何も書かれていない場合は、無理に注意文を作文せず、
  その部分は空欄にするか削除する（2026-08-05の石川ビーチ修正で、AIが
  「遊泳の際は現地の掲示・気象情報をご確認のうえご注意ください」という
  自作の注意文をnoteに書いてしまい、出典に存在しない文言を再び追加する
  結果になった。出典には実際には別の注意事項が記載されていた）
- 既存データも含め、noteとsourceUrlの不一致に気づいたら、`.claude/skills/poi-survey/SKILL.md`
  のこの方針に沿って速やかに修正し、修正履歴（`revisionHistory`、後述）に記録する

**「事実の再構成」と「AIの評価・要約」を区別する（2026-08-06・重要）**
クリームソーダ（id=1）のnote「営業スタイルが複雑。訪問前に公式サイトで要確認」は、
出典に虚偽の記載はなかったものの、「複雑」「要確認」という評価・要約の言葉自体は
出典に存在せず、AIが自分の言葉で書いていたことが判明した。事実は正しくても、
表現がAIの創作である点で石川ビーチの件と同種の問題。以下のルールを徹底する。

1. **出典にそのまま使える一文がある場合**：意訳・要約せず、その言葉をそのまま使う
   （可能なら「」で引用であることを示す）
2. **出典が事実の断片（数字・曜日・名称など）しかない場合**：それらの事実だけを
   組み合わせて書いてよい。ただし**「複雑」「名店」「人気」「安全」「本格」のような
   評価・印象を表す言葉は、出典にその言葉自体が使われていない限り書かない**
   （例：「月・木・金はランチ、土日はディナー」のように事実だけを書くのはよいが、
   そこから「営業スタイルが複雑」と評価を加えるのはNG）
3. **出典に何も書かれていない、または上記1・2のどちらも作れない場合**：
   無理に備考を書かず、空欄にする
4. 迷ったら「この一文は出典のどの言葉から来ているか、指させるか？」を自問する。
   指させない言葉が一つでもあれば、その部分は書かない

**このルールは「機械的な二重チェック」ではなく「書く時点での自己チェック」に
留まる点に注意（2026-08-10追記・重要）**
Step 3の検証員/懐疑係は**店舗の実在**を確認するものであり、`note`の個々の記述
（立地情報等）が出典に実在するかまでは検証していない。上記1〜4は書く時点の
指示であり、それ単体では見落としを機械的に防げない（実例：エステサロンDOUBLE
の備考「国道329号(石川バイパス)沿い」が、このルール導入〈2026-08-06〉より前の
2026-07-24に、出典に裏付けの無いまま追加されていたことが2026-08-10に発覚。
ルール導入後の新規追加でも、書く側が不注意なら再発しうる点は変わらない）。
- **立地表現（「〇〇沿い」「〇〇の近く」等）は特に捏造が起きやすいので要注意**
- **複数店舗をAgentツールで並行検証する場合**は、各Agentへのプロンプトに
  「noteに書く各文について、出典のどの記述に基づくか報告に明記させる」よう
  指示し、根拠を示せない記述は採用しない（Step3の検証員/懐疑係と同様、
  存在検証だけでなくnote内容についても複数の目でチェックする）

### Step 4: データ登録

**新ジャンルのカテゴリ確認（2026-08-10新設・重要）**
`restaurants-data.js`にデータを追加する前に、その店舗・施設の`genre`が
`script.js`の`CATEGORIES`配列（大分類・小分類）のどれかにマッチするか必ず確認する。
- マッチする → そのまま進めてよい
- **どれにもマッチしない**（例：鍵屋・水道屋のような新業種） →
  データだけ追加しても`macroOf()`のキャッチオール仕様により自動的に
  「食事処」扱いの見た目になってしまう（ピン色・絞り込み等が実態と合わなくなる）。
  **必ずユーザーに「新しいカテゴリ（またはsub）として`CATEGORIES`に追加するか」
  を確認してから登録する。** 黙って食事処扱いのまま登録しない

`restaurants-data.js` に既存と同じ形式で追加。**必ずコメントに調査日と手法を記録**：

**id・codeの採番ルール（重要・2026-07-30改定）**
- `id`：既存データ全体の**最大id + 1**を使う。地域をまたいで通し番号1本（地区ごとに0から振り直さない）。
  一度振った`id`は、その店が掲載終了（`status: hidden`等）になっても**絶対に再利用しない**（欠番のまま）。
- `code`：`都道府県市区町村コード-地区略称-連番`（例:`47213-IS-0056`）。**連番部分は`id`と同じ全体通し番号を使う**
  （`id + 1`を4桁ゼロ埋め）。地区ごとに`0001`から数え直さない
  （旧ルールは地区内連番だったが、複数地区展開時に`id`との対応が崩れるため統一した）。
  地区略称は石川=`IS`。他地区を追加する際は新しい略称を決めてこの表に追記する。
- `status`：通常は`"published"`
- `tel` / `lastChecked`：わかる範囲で記入。不明・未調査なら空文字のまま

**画面に表示する「店舗番号」について**
利用者・店舗側からの問い合わせ用に、`detail.html`の店舗詳細ページには`id`から自動生成した番号
（`No.000007`のような形式、`id + 1`を6桁ゼロ埋め）を表示している。この番号は地名・行政コードを
含まないため、地域が増えても値が変わらない。`restaurants-data.js`側にフィールドとしては持たせず、
表示時に`detail.html`内で計算している（`code`とは別物）。新規追加時に`code`さえ正しく振れば、
表示用番号は自動的に正しくなる。

**情報源が複数ある場合（`sourceUrls`、任意）**
通常は`sourceUrl`（単一）だけでよいが、ある店舗について食べログ・個人サイト等
**複数の情報源を読者に案内したい場合**は、`sourceUrls`（配列）を追加すると
`detail.html`のリンク欄に「情報源①：食べログ」「情報源②：〇〇」のように
番号付きで自動的に並べて表示される（2026-08-05導入。1件なら`sourceUrl`のまま
でよく、`sourceUrls`は無くて構わない）。

```javascript
sourceUrls: ["https://tabelog.com/...", "https://個人サイトのURL/..."],
```

- サイト名（①②の後ろの文言）は`sourceUrl`と同じくドメインから自動判定される
  （`THIRD_PARTY_SITE_LABELS`等に無いドメインはホスト名がそのまま出る）
- `sourceUrl`と`sourceUrls`を両方書いた場合は`sourceUrls`が優先される
- Step 3.5（営業時間・定休日の出典）で使う`sourceUrl`は従来通り単一のまま
  （本文中の出典表示は変更なし。`sourceUrls`はリンク欄の情報源ボタンのみに影響）

**修正履歴（`revisionHistory`、既存店舗の店名・住所等を修正したときは必ず追加）**
新規追加時ではなく、**既存店舗のデータを後から修正したとき**に使う。
`detail.html`の「店舗紹介・詳細情報」の下に「修正履歴」として表示され、
備考直後には「最終情報確認または修正日：YYYY-MM-DD（前回より修正あり/なし）」
も自動表示される（`revisionHistory`の最新日付と`lastChecked`が一致する回だけ
「修正あり」と表示される仕組み）。2026-08-05導入。

```javascript
lastChecked: "2026-08-05",  // 修正・再確認した日
revisionHistory: [
  { date: "2026-08-05", type: "manager", note: "（何をどう直したか。修正前→修正後、根拠となった情報源を書く）" }
],
```

- **配列への追加は必ず末尾（新しいものを一番最後）に追記する**（古い順で保持）。
  画面表示だけは`detail.html`側で自動的に新しい順（配列を反転）にして見せている
  （2026-08-06〜）ので、データ側の並び替えは不要・してはいけない
  （末尾追記の前提が崩れると「最終修正日」判定ロジックが壊れる）
- `type`は3種類。**「対話を経たかどうか」ではなく「具体的な修正内容・文言を
  誰が決めたか」で分ける（2026-08-08改定・重要）**：
  - `"ai"`：具体的な修正内容・文言をAIが調査・判断して決めた場合。
    ユーザーからの依頼・指示（「確認して」「直して」等）がきっかけであっても、
    実際に何をどう直すかをAIが調べて決めたのであればこちら。
    定期自動更新もこちら。**このスキルの手順で行う修正のほとんどはこの type になる**
  - `"manager"`：ユーザー自身が具体的な修正内容・文言を指定・決定した場合
    （AIは指示された通りに反映するだけ）
  - `"owner"`：店舗主自身による修正
  - 2026-08-08以前は「ユーザーとの対話を通じた修正はすべてmanager」という
    誤った基準を使っていたため、該当する既存の修正履歴をaiに一括修正した
- 店名・住所・営業時間など、**読者が見る内容を実際に書き換えたときだけ**追加する
  （単に情報源を1件足しただけ、等の軽微な変更では不要）
- `note`（備考）には「〜に修正しました」のような編集メモを書かない。
  備考は場所そのものの説明に徹し、修正の経緯は`revisionHistory`側に書く
