# デザイン品質スキル（石川マップ）

見た目の"貧相さ"や動きの"カクつき"は、技術的な限界ではなく実装の細部で起きる。
ただし、石川マップは数週間かけて1px単位で調整してきた既存コードの上に成り立っているため、
このスキルは「新しく作る部分」を主な対象とし、**既存の調整済み箇所には1箇所ずつ確認しながら適用する**。

## 0. 適用範囲（最初に確認する）

- **迷わず適用する**：新しいコンポーネント・ページを作るとき／「見た目を全体的に整えたい」と明示的に依頼されたとき
- **このスキルの4項目チェックを毎回持ち出さない**：既存の1箇所を「もう少し右に」「文字を大きく」のような単純な微調整をするとき
- **既存部分に適用したいときは、対象箇所を1つずつ明示してユーザーの確認を取ってから進める**（例：「メニューの開閉にtransitionが無いので、フェードを足すと滑らかになります。直していいですか？」）。「既存部分には一切触らない」という意味ではなく、**気づいた箇所を確認なしに一括で書き換えない**、という意味
- 既存の調整済みCSS値（例：`padding: 6px 14px 12px` のような個別調整値）を、下記4章の刻み幅ルールに合わせて**勝手に丸めない**

### 既存部分への適用の進め方（実績あり）
1. まず石川マップ全体から「クイックウィン（すぐ効果が出て、リスクが低い箇所）」を洗い出す
2. 見つけたものを一覧でユーザーに提示し、どれから手をつけるか一緒に決める
3. 1箇所ずつ修正→プロジェクト標準の確認フロー（スマホ幅375pxのローカルプレビュー）で検証→問題なければコミット・プッシュ、を繰り返す
4. デザインシステム（余白・フォントサイズの統一）のような大掛かりな話は、急がずページ単位などで区切って進める

（2026-08-22、⚙設定メニューのフェード化・写真ライトボックスのフェード化・ミニマップのリサイズ処理デバウンス化の3件をこの手順で実施し、無事本番反映済み）

## 1. まず原因を特定してから直す

「カクつく」「もっさりする」という感覚は主観的なので、いきなり全項目のルールを適用するのではなく、
まずブラウザの開発者ツール（Performanceタブ・Lighthouse等）や `Grep` でのコード調査で実際に重い箇所・
アニメーションが欠けている箇所を確認し、原因を絞り込んでから該当箇所だけを直す。当てずっぽうに全体を書き換えない。

## 2. 画像の最適化（画像を実際に使う場合のみ）

石川マップは現状、店舗写真（`photos`）が空のデータが大半で、ビルド工程（npm等の自動変換）を
持たない素のHTML/CSS/JSサイトである。画像最適化ルールは**実際に画像を追加・表示する機能を作るとき**に適用する：

- 表示サイズより大きい画像を読み込ませない（例: 幅300pxで表示するなら300〜600px幅）
- `loading="lazy"` を画面外になり得る画像に付与する
- 可能ならWebP形式を使う（変換は手動でよい。自動パイプラインは不要な規模）
- アイコン・ロゴはSVGを使う
- `<img>` には `width`/`height` を指定し、読み込み中のガタつき（CLS）を防ぐ

## 3. アニメーション・トランジション

- 状態変化（ホバー、開閉、表示/非表示）にはtransitionを付ける。**`all` は使わず、対象プロパティを明示する**：
  ```css
  transition: transform 0.2s ease-out, opacity 0.2s ease-out;
  ```
  （`all`は意図しないプロパティまで巻き込み、かえって重くなったり不自然な動きになったりするため使わない）
- アニメーションさせるプロパティは `transform` と `opacity` を優先する（`width`や`top/left`は再レイアウトが発生し重い）
- 急に動く・止まるのはNG。`ease-in-out`や`cubic-bezier`で緩急をつける
- **OS側の「視差効果を減らす」設定を尊重する**：
  ```css
  @media (prefers-reduced-motion: reduce) {
    * { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
  }
  ```
- `display: none ⇄ block/flex` の瞬間切り替えをフェードさせたい場合は、`opacity`だけでは
  「非表示から表示になる瞬間」「表示から非表示になる瞬間」の両方で正しくアニメーションしない
  （直前の描画状態が無いと補間できないため）。次のパターンを使う：
  - 開くとき：`display`を先にセット→**二重`requestAnimationFrame`**の中でフェード用クラスを追加
    （Safari等で1回のrAFだと稀に発火しない端末があるため二重にする）
  - 閉じるとき：フェード用クラスを先に外す（フェードアウト開始）→
    `setTimeout`でtransitionの時間分待ってから`display:none`を適用
  - 実例：`script.js`の`showMain()`/`closeMenu()`（⚙メニュー）、`detail.html`の
    `openLightbox()`/`closeLightbox()`（写真ライトボックス）を参照

## 4. デザインシステム（新規部分に限定）

- **新しく作るUI**では、フォントサイズ・余白を「思いつきの数値」ではなく決まった刻み幅から選ぶ：
  - フォントサイズ: 12 / 14 / 16 / 20 / 24 / 32px
  - 余白(margin/padding): 4 / 8 / 12 / 16 / 24 / 32 / 48px
- 新規のCSS変数として定義してよい（例: `:root { --space-2: 8px; --font-base: 16px; }`）が、
  **既存のCSSに後から一括適用するリファクタリングは、別途ユーザーの承認を得てから行う**（既存の調整値を壊すリスクがあるため）
- 行間(line-height)は本文で1.5〜1.7を目安にする

## 5. パフォーマンス（無駄な再描画を減らす）

- スクロール・リサイズなど頻繁に発火するイベントには`debounce`/`throttle`を使う
  （前回のタイマーを`clearTimeout`してから新しくセットする方式。実例：`script.js`の
  ミニマップ`resize`イベントハンドラ参照）
- DOM操作はまとめて行い、ループ内で1要素ずつ`style`を変更するコードは避ける
- 不要な`console.log`や監視処理を本番コードに残さない
- 一覧表示（店舗一覧等）へのページネーション・仮想スクロール導入は、件数が数百件を超えて
  実際に重くなってから検討する（現状74件程度では不要。先に導入すると複雑さだけが増える）

## 実装時の確認フロー

新しいコンポーネントを作る・見た目や動きを意図的に磨き込むときは、以下を自問する：

1. （新規の場合のみ）画像は最適化されているか？
2. 状態変化のtransitionは対象プロパティを明示し、reduced-motionに配慮しているか？
3. （新規の場合のみ）フォントサイズ・余白は決めた刻み幅から選んでいるか？既存の調整値を無断で変えていないか？
4. 頻繁に発火する処理に無駄な重さはないか？

修正後は、このプロジェクトの標準の確認フロー（スマホ幅375pxのローカルプレビューで動作確認・
コミット前にユーザーへpush確認）も必ず行う。
