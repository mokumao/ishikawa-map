# 他地域への展開方針（検討中）

石川マップを将来、具志川・勝連・与那城などへ展開する場合の構成と進め方を整理する。

この文書は検討記録であり、展開先や構成を決定するものではない。実際の着手は、管理者が対象地域と作業範囲を指定してから行う。

長期目標は沖縄県全体でも利用・運用できるSkill体系とする。ただし、全県用機能を先に作り込まず、後から変えにくい共通ルールを整えて段階的に検証する。詳細は[沖縄県全体を見据えたSkill体系](okinawa-skill-roadmap.md)に記録する。

## 現在分かっていること

- `script.js`や`index.html`には「石川」という名称が複数箇所に直接記述されている。
- 店舗IDは地域をまたぐ通し番号として利用できる。
- 地区略称を含む`code`は、地区を追加できる形式になっている。
- 行政区域境界線、店舗・施設データ、地区紹介、ニュース取得条件は、地区ごとに調査・作成が必要になる。
- `poi-survey`、`area-profile`、`ishikawa-local-news`などの調査手順は、他地区にも再利用できる。
- 地区を切り替える共通サイトにする場合、現在動作している石川マップ本体の大規模な再設計が必要になる。

## 検討した構成

### 案1：地区ごとに別リポジトリ・別サイトを作る

- 現在の石川マップをコピーし、新しい地区用に変更する。
- 既存の石川マップへ与える影響が小さく、最初の展開に着手しやすい。
- 地区数が増えると、機能修正や端末対応を各サイトへ繰り返し反映する必要がある。

### 案2：1つのサイト内で地区を切り替える

- 現在のリポジトリへ地区設定を追加し、データや境界線などを切り替える。
- 共通機能の修正を全地区へ一度に反映できる。
- 現在の石川専用コードを整理する大規模な改修が必要で、既存動作を壊すリスクがある。

### 案3：同じリポジトリ内に地区別フォルダを作る

- 例として`gushikawa/`のような別フォルダへ、石川マップを基にした地区版を作る。
- 現在の石川マップ本体を保護しながら、別リポジトリの増加を避けられる。
- 2地区の実運用後に共通部分を比較し、必要なものだけを共通化できる。
- 共通化するまでは、地区ごとに重複するコードが残る。

## 現時点の推奨方針

現時点では案3を第一候補とする。ただし、まだ正式決定ではない。

1. 現在の石川マップは、安定運用を優先して大規模改修しない。
2. 次の展開地域が正式に決まるまで、全面的な共通化を行わない。
3. 最初の他地区は、現在の石川マップから隔離した地区別フォルダで試作する。
4. 2地区の実データと運用経験を基に、共通部分と地区固有部分を確認する。
5. 3地区目へ進む前に、共通化または別サイト継続を改めて判断する。

## 新地区を調査する順序

1. `$area-boundary-survey`で地区の定義、外周、境界線を調査・検証する。
2. 管理者が根拠と地図上の青線を確認し、掲載対象範囲を確定する。
3. `$area-profile`で確定範囲の地理、歴史、人口、文化を調査する。
4. `$poi-survey`で確定範囲内の店舗・施設を調査する。
5. ニュース取得条件、表示名、初期位置、端末別表示を設定・検証する。

境界が確定できない場合は、推測で店舗調査や公開へ進まず、資料間の違いと不足している確認を記録して保留する。

## 地区ごとに必要となる作業

- 対象地区の範囲と行政区域境界線の確認
- 店舗・施設データの新規調査
- 地区紹介ページの調査・作成
- 地図の初期位置と縮尺の設定
- ページタイトル、地区名、SEO情報の設定
- ニュース取得対象と検索条件の設定
- スマートフォンを含む端末別表示の確認
- 公開後の修正、問い合わせ、定期確認の運用設計

## 今後決めること

- 最初に展開する地区
- 展開を開始する条件と時期
- 別リポジトリ、地区別フォルダ、共通サイトの最終選択
- サイト全体の名称
- 地区を選択・移動する画面の必要性
- URL構成
- 店舗調査の件数、対象カテゴリ、掲載基準
- `$area-boundary-survey`を具志川の実例で検証し、必要な情報源や例外を追加する
- 地区が増えたときの更新作業量と管理方法

## 判断する時期

次の地区へ実際に着手する直前に、この文書を見直して構成を決定する。特別な事情がなければ、隔離した構成で2地区目を試作し、2～3地区が揃う前に共通化を再検討する。
