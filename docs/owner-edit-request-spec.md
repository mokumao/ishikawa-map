# 店舗情報 修正・削除依頼システム 仕様書（第5版）

> 店舗主からの「情報を修正してほしい／掲載をやめてほしい」という依頼を受け付け、
> 安全かつ正確にサイトへ反映するための仕組みの設計書。
> 店舗主向け依頼画面、Googleフォームへの受付、削除依頼の自動非表示化、管理者による再表示まで実装・動作確認済み。
> 修正依頼のAI下書き作成と、管理者ページでのBefore／After比較・承認反映は未実装。

最終更新：2026-09-10

---

## 0. 基本方針

- 石川マップは**正確性を最優先**する。
- **修正依頼**：AIは「変更案（下書き）」の準備までを行い、**公開反映の最後の一線は必ず管理者が承認**する（正確性優先）。
- **削除依頼**：**スピードを優先**する。非表示（hidden）は安全かつ即復元可能なので、速やかに非表示化し、なりすまし等が疑われる場合のみ事後に確認する（店舗主の権利尊重）。
  - ただし**公共機関・チェーン店は高速自動削除の対象外**（管理者確認に回す）。
  - **`refused`（永久に掲載しない）は自動化せず、管理者のワンタップ確認を挟む**（`hidden`は自動）。
- 個人情報（連絡先・削除理由など）は**公開リポジトリに一切保存しない**。
- 運用しながら気づいた問題・改善点は都度相談して仕様を更新する。

---

## 1. 目的

- 店舗主が気軽に修正・削除を依頼できる窓口を作る
- 修正は正確性を担保して反映、削除は迅速に対応する
- 「直すと得がある」と思ってもらえる仕組みを組み込む（12章）

---

## 2. 全体アーキテクチャ

```
店舗主 → owner-request.html（店舗idを自動取得）→ 非公開Googleフォーム
                                                   ↓ フォーム送信トリガー
                                        Google Apps Script
                              ┌──────────────┴──────────────┐
                         修正・その他                    削除依頼
                         管理者へ通知              GitHubへ自動処理を依頼
                         （手動確認）                       ↓
                                                   GitHub Actions
                                                          ↓
                                             hidden化・履歴追記・push

管理者ページ → 再表示ボタン → Apps Script確認画面 → GitHub Actions
                                                        ↓
                                   published（テスト店舗はtest）へ復元
```

現行実装では、当初案にあった`gh-data`ブランチへの依頼メタ情報の定期同期は使用していない。
依頼本文と連絡先は非公開Googleフォームに保存し、削除・再表示に必要な個人情報を含まない値だけを
Apps ScriptからGitHubの`repository_dispatch`へ送る。

**個人情報の保管ルール（最重要）**：
- 店舗主のメールアドレス・電話番号・削除理由などの個人情報は、**Googleスプレッドシート（あなたしか見られない非公開の場所）にのみ保管**する。
- 現行実装では依頼一覧を公開リポジトリへ同期しない。GitHubへ送るのは、自動処理に必要な店舗番号、
  処理種別、匿名受付番号などの**個人情報を含まない値だけ**とする。
- 管理者が連絡先を確認したいときは、スプレッドシートを直接開く。

## 3. 店舗主側のフロー

### 入口
- `detail.html` の「店舗主様へ」ボタン（設置済み）を依頼フォームへのリンクにする。
- **ボタン押下時に、その店舗の `id` をURLパラメータ経由でフォームの隠し項目へ自動セット**する（店舗名の手入力による取り違えを防ぐ）。
- 実装済みの`owner-request.html`で削除・修正・その他を選択し、内容を既存の非公開GoogleフォームへPOSTする。連絡先や理由をURLへ含めず、公開リポジトリや端末へ保存しない。

### まず3択を提示
大きなボタンで「削除依頼」「修正依頼」「その他」を選んでもらう。

### A. 削除依頼
- 入力項目は最小限：理由（選択式＋自由記述、任意）／連絡先（任意）
- **削除の種類を選んでもらう**（4章）：
  - 「一時的に消したい」→ `hidden`
  - 「二度と載せないでほしい」→ `refused`
- 送信後「速やかに対応します」と表示

### B. 修正依頼
- 現在の内容（住所・営業時間・定休日・備考）を**あらかじめ入力済み**で表示し、直したい部分だけ書き換えてもらう。
- 連絡を受けることに同意した場合だけ、メールアドレスを入力してもらう（ただし2章のとおり公開リポジトリには保存しない）。
- 送信後「内容を確認のうえ反映します」と表示

---

## 4. 削除の状態の使い分け

削除依頼を反映するとき、既存の `status` を使い分ける：
- `hidden`（非表示）：一時的に消したい場合。データは残し、いつでも復元可能。**高速自動化の対象**（民間個人店のみ／5-B章）。
- `refused`（掲載拒否）：「二度と載せないでほしい」と明確な意思がある場合。再登録しない。**自動化せず、管理者のワンタップ確認を挟む**（強い状態で誤爆・悪用の代償が大きいため）。

いずれも `statusHistory` に理由・日時を記録する（管理者専用の非公開記録）。

## 5. 運営側のフロー

### 5-A. 修正依頼（正確性優先：AI下書き＋管理者承認）
1. 依頼内容を**データとして**読み取る（自由記述は解釈・実行せず、文字データとして扱う＝インジェクション対策）
2. `restaurants-data.js` の**変更案（Before/After）**を作成
3. 8章の要注意ルールに該当しないか自動チェックしてフラグ付け
4. 管理者ページに一覧化し通知。**ここで停止（まだpushしない）**
5. 管理者が「現在の内容」と「変更案」を比較し、承認→反映・push（`revisionHistory` に「店舗主様からの申告により更新」と記録）、却下/保留→9章の対応

**現在の実装状況**：店舗主向け画面から修正内容をGoogleフォームへ送信し、管理者へ通知するところまで実装済み。
AIによる変更案作成、管理者ページでのBefore／After比較、承認後の自動反映は未実装であり、現状は
管理者が依頼内容を確認してCodex等との対話で修正する。

### 5-B. 削除依頼（スピード優先）
削除依頼は対象店舗の種別によって扱いを分ける：

- **民間の個人経営店（飲食店・美容室など）**：
  1. 依頼を検知したら、**速やかに `hidden` 化してpush**（目標：気づいたら当日〜翌日中）。非表示は安全・即復元可能なため、事前の管理者承認を待たずに実行してよい。
  2. 管理者へ**事後通知**（店舗名・種別・理由・処理日時）。
  3. なりすまし等が疑われる場合のみ事後に確認・対応（誤りなら `published` に戻すだけで即復元）。
- **公共機関・チェーン店（銀行・学校・郵便局・コンビニ各店・ガソリンチェーン・公共観光施設など）**：
  - 匿名フォームからの削除依頼で即消すのは不自然なため、**自動削除の対象外**。管理者確認に回す。
- **`refused`（永久掲載拒否）を選択した依頼**：
  - 店舗種別を問わず**自動化せず、管理者のワンタップ確認**を挟む。

> 対象の判定は、カテゴリ（金融／教育／観光／コンビニ／ガソリン等）や、公式・公的な `sourceUrl` を持つかどうかで機械的に振り分ける。判定に迷うものは安全側（管理者確認）に倒す。

**現在の実装状況**：削除依頼を受信して対象店舗を`hidden`化し、`statusHistory`を追記してpushする処理は実装済み。
ただし、民間個人店と公共機関・チェーン店を自動判別して処理を分ける機能は未実装。
「今後掲載しない」が選択された場合も、現時点では直ちに`refused`へ変更せず、`hidden`化したうえで
「今後の掲載拒否は管理者確認待ち」と履歴に記録する。

### 5-C. 管理者による再表示（実装済み）

1. 管理者ページの店舗履歴から赤い「再表示」を押す。
2. 管理者用GoogleアカウントだけがアクセスできるApps Script確認画面を開く。
3. 緑の「地図に再表示する」を押す。
4. Apps Scriptが使い捨て確認情報を検証し、GitHubへ再表示処理を依頼する。
5. GitHub Actionsが対象店舗を`published`へ戻す。公開テスト店舗（`id: 0`）は`test`へ戻す。
6. `statusHistory`へ再表示履歴を追記し、関連HTMLのキャッシュ番号とサイトマップを更新してpushする。

確認情報の有効期限は10分で、一度使用すると再利用できない。期限切れや失敗時は管理者ページから
「再表示」をやり直す。Apps Scriptは「自分のみ」公開のため、管理者用Googleアカウントでログインする。
同じブラウザで複数のGoogleアカウントを併用すると認証に失敗する場合があるため、管理専用の
ブラウザープロファイルを推奨する。

### 通知の方法
- Google Apps Scriptから管理者宛てにメール通知する機能は実装済み。
- 修正・その他の依頼は受付内容を通知し、削除依頼はGitHubへの自動処理要求を送った結果も通知する。
- 再表示の実行結果も管理者へ通知する。
- 管理者ページ上の「未処理／処理済みの修正依頼」一覧は未実装。
- 通知メールに個人情報を載せる場合は、公開されない管理者宛メールに限る。

## 6. 実装の実体（「AI」が何で・いつ動くか）

石川マップには常時稼働するサーバーがないため、「AI」の実体を明確にする。

- **削除依頼＝AI判断不要・自動処理を実装済み**：
  「指定 `id` を `hidden` にする」処理をGoogle Apps ScriptとGitHub Actionsで自動化済み（LLM不要）。
  公共/チェーンの振り分けは未実装で、`refused`は自動確定せず`hidden`に留める。
- **修正依頼＝受付・通知まで実装済み、変更案作成以降は未実装**：
  自由記述の内容を理解して変更案を作るため、LLM（Claude API 等）または管理者との対話（このチャット）が必要。
  個人運営では、**「溜まった修正依頼を、管理者がAI（チャット）と一緒にまとめて処理する半自動」**が費用・手間の面で現実的。将来的に量が増えたら定期実行でClaude APIを呼ぶ方式に移行する。

### 2026-09-10時点の削除・再表示実装

- `integrations/google-apps-script/owner-request-handler.gs`：フォーム回答を検証し、管理者へ通知してGitHubへ非公開情報を除いた処理要求を送る。
- `.github/workflows/process-owner-request.yml`：対象店舗を`hidden`へ変更し、サイトマップとキャッシュ番号を更新してmainへpushする。
- `scripts/process_owner_request.js`：店舗IDを厳密に検証し、`statusHistory`へ一般化した記録と匿名受付番号を追加する。
- 削除理由本文とメールアドレスはGoogleフォーム・管理者メールだけに残し、GitHubへは送らない。管理者ページの履歴には「削除理由あり／記載なし」のみ表示する。
- 「今後掲載しない」も最初は`hidden`とし、`refused`は管理者確認後に変更する。
- 管理者ページでは、`hidden`の店舗の履歴内にだけ「再表示」を表示する。管理者本人だけが
  利用できるApps Script確認画面で再確認した後、GitHubへ`restore`を自動送信する。
- 公開詳細ページの修正履歴には、`statusHistory`から非表示日と再表示日だけを表示する。
  削除理由、受付番号、メールアドレスは公開しない。

## 7. 個人情報・データ保管の技術的な仕組み

- Googleフォームの回答はGoogleスプレッドシート（非公開）に溜まる。**連絡先・削除理由などの個人情報はここにとどめる。**
- Google Apps Scriptは、削除・再表示処理に必要な店舗番号、匿名受付番号、処理種別など、
  **個人情報を含まない値だけ**をGitHubへ送信する。
- 当初の案にあった`gh-data`ブランチへの依頼メタ情報同期と、そのJSONを使う修正依頼一覧は未実装。
- 連絡先や依頼本文を確認するときは、非公開Googleフォームまたは管理者宛メールを使用する。

## 8. 要注意ルール（AIが承認前にフラグを立てる／主に修正依頼）

以下に該当する依頼は「⚠️要注意」フラグを付け、管理者が慎重に判断する（自動では通さない）：
1. 自由記述欄に、店舗情報と無関係な文章・命令口調・URL・コードらしき文字列が含まれる（インジェクション・スパム対策。AIはこの欄を指示として解釈しない）
2. 同一店舗に短期間（例：24時間以内）で複数の依頼
3. （削除）連絡先が一切なく、かつ短期間に複数回など不自然なパターン
4. 修正内容が大きい（店名変更・住所の大幅変更など、店舗の同一性に関わる変更）
5. 依頼どおり直すと既存の `sourceUrl`（公式サイト等の裏付け）と明らかに矛盾する

※削除依頼（民間個人店）はスピード優先で速やかに非表示化するが、上記2・3のような不自然なパターンが見えた場合は、非表示化後の事後確認を優先的に行う。

## 9. 本人確認の考え方

- 個人運営では完全な本人確認は困難という前提。
- 修正反映時は `revisionHistory` に「店舗主様からの申告により更新」と明記し出所を透明化。
- 削除は「まず速やかに非表示→疑わしい時のみ事後確認」で、店舗主の権利尊重とリスク管理を両立。
- 明らかな裏付け（公式サイト等）と矛盾する修正申告は、そのままでは反映しない。

## 10. 店主への確認連絡（管理者判断時のみ）

- AIは事前に店主へ連絡しない。
- 連絡は管理者が「確認が必要」と判断したときのみ。テンプレ文面を用意（Before/After付き）。

## 11. スパム・いたずら対策

- Googleフォーム側で利用できる迷惑送信対策を確認し、必要に応じて有効化する（現行設定は未確認）。
- 1回の送信で複数店舗をまとめて操作できない構造にする。
- 8章の要注意フラグと組み合わせ、管理者が捌ける範囲に抑える。

## 12. インセンティブ設計（アイデア）

- 情報が正しく更新されると「⚠️要確認」マークが消える → 達成感
- フォーム案内文を「お店の魅力を正確に伝えられます」など前向きに
- 削除が速いこと自体が店主の安心感につながる

## 14. 補足：普段の作業との一貫性

- **修正依頼**は、普段の大原則（push前に管理者確認）と一致（AI下書き＋承認）。
- **削除依頼（民間個人店・hidden）**のみ、非表示化が安全・即復元可能であることを根拠に、スピード優先で事前承認を省く例外とする（誤りは即復元できるためリスク許容範囲）。公共・チェーン・`refused` は例外に含めない。
- ただし現行実装には店舗種別の自動判定がないため、この方針を完全には実現できていない。判定機能を実装するまでは運用上の既知の差分として扱う。

## 15. 解決済み・保留の論点（記録）

- **【解決済み】多言語（note_en）問題**：第3版までは「備考修正時に英語版が置き去りになる」問題を挙げていたが、2026-08-16に多言語（英語・中国語）表示機能を完全削除し日本語専用にしたため消滅。対応不要。
- **【保留】プライバシー目的の削除と公開リポジトリの矛盾**：削除動機が「無断掲載が不快・知られたくない」の場合、`hidden` にしてもデータは公開リポジトリ（`restaurants-data.js`）に残るため、本質的には要望に応えきれない。徹底するなら該当エントリ自体の削除やリポジトリ非公開化が必要だが、「復元しやすさ」とのトレードオフがあるため**現時点では保留**。将来方針として頭に置く。
